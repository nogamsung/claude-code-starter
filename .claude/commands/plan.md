argument-hint: <구현할 기능 설명>

코드를 작성하기 전에 설계를 먼저 검토합니다.

**요청:** $ARGUMENTS

---

## 진행 순서

### Step 1 — 요청 분석

요청을 읽고 다음을 판단합니다:

**명확한 요청인가?**
- 무엇을 만들지 알 수 있는가?
- 어떤 파일/레이어가 영향받는지 알 수 있는가?
- 요구사항에 모순이나 빠진 부분이 없는가?

**모호한 요청이라면** → Step 2로 이동
**명확한 요청이라면** → Step 3으로 이동

---

### Step 2 — 소크라테스식 인터뷰 (모호한 경우)

다음 질문 중 필요한 것만 골라 사용자에게 묻습니다. **한 번에 최대 3개까지만** 물어봅니다.

**도메인/범위 질문:**
- 이 기능의 핵심 사용자 시나리오가 무엇인가요?
- 어느 레이어/모듈에 추가하는 건가요?
- 기존 코드와 어떻게 연결되나요?

**비즈니스 규칙 질문:**
- 예외 케이스가 있나요? (빈 목록, 권한 없음, 중복 등)
- 유효성 검사 규칙이 있나요?
- 기존 동작과 호환이 필요한가요?

**기술 결정 질문:**
- 새 파일을 만드나요, 기존 파일을 수정하나요?
- 테스트도 함께 작성할까요?
- 특별히 선호하는 구현 방식이 있나요?

사용자 답변을 받은 후 Step 3으로 이동합니다.

---

### Step 3 — 구현 계획 작성

CLAUDE.md의 아키텍처 규칙을 참고하여 계획을 작성합니다.

다음 형식으로 제시합니다:

```
## 구현 계획

### 변경할 파일
- [신규/수정] `경로/파일명.ext` — 변경 이유

### 영향받는 범위
- 연쇄적으로 영향받는 파일 목록

### 구현 순서
1. 첫 번째 단계
2. 두 번째 단계
...

### 주의사항
- CLAUDE.md 규칙 중 이 작업에 특히 관련된 것
- 예상되는 엣지 케이스

### 테스트 계획
- 작성할 테스트 케이스 목록
```

---

### Step 4 — 확인 요청

계획을 제시한 후 반드시 물어봅니다:

> **이 계획대로 진행할까요? 수정이 필요한 부분이 있으면 알려주세요.**

사용자가 승인하면 해당 스택의 generator/modifier agent를 사용해 구현을 시작합니다.
사용자가 수정을 요청하면 계획을 업데이트하고 다시 확인합니다.

---

## 핵심 원칙

> 코드를 먼저 짜고 나중에 방향을 수정하는 것보다,
> 방향을 먼저 합의하고 코드를 짜는 것이 항상 빠릅니다.
